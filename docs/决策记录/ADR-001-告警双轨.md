# ADR-001 告警双轨:Device Profile alarm rules 与站点规则链的分工

状态:**提议**(待 D1 议定)
关联:架构 v2 §0 ⑥、§5.2 阶段 4、§10「告警双轨」;计划 T1.3 `profile-alarms.ts`、T2.5、T4.1

## 背景

原稿把全部阈值告警编译到 Device Profile。生产库一个 IED Profile 服务多个项目,站点级阈值写进 Profile 会跨站点泄漏;Profile 规则也没有「变化才报」语义。现有编译器已有站点告警规则链路径并在镜像实测。

**镜像实测补充(2026-09-03)**:库内 11 个 Device Profile 目前**都没有** alarmRules;联调站点润扬大桥的 11 台子设备(PCS / BMS / 电表 / 液冷机 / 传感器 / 测控…)**全部挂在 `default` Profile**,与 `thermostat` 等杂项设备同槛。这意味着「通讯中断写进 Profile」在该站点会作用到库里所有 `default` 设备。Profile 路线要成立,前提是先给设备分好专属 Profile(`ESS_PCS / ESS_BMS / METER …`)——这属于阶段 2「设备接入」的工程动作,不是工具的事。

**仙人山补充(2026-09-03,当前暂定联调站点)**:170 台设备中 129 台在 `default`,32 台 IED / 6 台 METER / 2 台 ATS 有专属 Profile——模板级告警一期只对这三个 Profile 可行。且现场 `COM` 是累加的通讯计数(非 0/1),「通讯中断」应编译为 TB Profile 的 **inactivity 事件**(`inactivityTimeout` + `Inactivity Event`)或站点规则链里「N 分钟内 `COM` 无变化」,不能写 `COM == 0`。

## 决定(推荐)

按**一句话判定规则**分流:

> 「这条告警的阈值和含义对该 Profile 下所有设备、所有站点都相同」→ Device Profile alarm rules;否则 → 站点告警规则链。

一期具体落位:

| 进 Profile | 留规则链 |
|---|---|
| 通讯中断(`COM` / 心跳超时,`inactivityTimeout`) | 电压 / 电流 / 功率越限(阈值随站点、随季节) |
| 设备自报故障位(`FAULT`、`CB` 异常等布尔量) | 「变化才报」类(状态翻转、开关动作) |
| | 跨设备条件(A 设备 X 且 B 设备 Y) |
| | 依赖 `calc_` 计算结果的告警 |

Profile 侧写入规则:只新增 / 更新 `alarmRules` 中 `alarmType` 以 `dt_` 开头、且 `additionalInfo.managedBy = 'deploy-tool'` 的条目;其他条目一律不碰。cleanup 只删自己的。

**兜底规则**:设备挂在 `default`(或任何被多类设备共用的通用 Profile)上时,工具**不向该 Profile 写任何规则**,该设备的全部告警一律走站点规则链,并在界面提示「设备未分专属 Profile,通讯中断类告警已降为站点级」。避免一条通讯告警波及全库杂项设备。

工具 UI:告警配置行加一个只读标签「Profile 级 / 站点级」,由工具按上表自动判定,不让工程人员选(避免误选泄漏)。

## 备选与放弃理由

- **全部走 Profile**:跨站点泄漏、无变化才报语义 → 否。
- **全部走规则链**:通讯中断类要给每个设备建一条规则,231 台 × N 站点规则链膨胀;且 TB 的 inactivity 事件天然在 Profile 层 → 否。
- **让工程人员选**:误选即泄漏到其他项目,风险大于收益 → 否。

## 对代码的直接影响

- `packages/compiler/src/profile-alarms.ts` 新增;`alarmMetadata()` 保留只处理站点级。
- tbsite / `.scadaproj` 的告警声明增加只读派生字段 `level: 'profile' | 'site'`(编译时计算,不存)。
- live 测试:Profile 幂等 + 只删自己的。
