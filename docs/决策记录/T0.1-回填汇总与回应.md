## 0. 最重要的一条新事实:TB 不是长期数据库

后端同事在 A4 写:「回写不了,遥测库预计 3–7 天清除」「扩展服务的数据:分钟的保存 3 个月,5 分钟–时–日–月–年永久保存」。

镜像核实(2026-09-04,`SSP1_GP1_IED1.P` 等 3 个 key):近 5 天每天约 14,700 个点,再往前只剩零星几个点——与「TB 只留几天原始遥测、长期归档在 kz 的库里」一致。

这改变了三件事:

1. `ts-history` 只能覆盖 **≤ 3 天**的窗口;7 天 / 30 天 / 逐月曲线必须从 kz 取。原稿与 v2 架构都默认 TB 是历史数据源,这个假设不成立。
2. ADR-004 的路线 B(kz 回写 TB)不可行,而且即使回写了也会被清掉。**必须走路线 A:契约加 `mode: 'ext'`,tbClient 加 kz 实现**,且不是「过渡」,是一期正式路线。
3. 我方 T2.5 里「多级归档 5 分钟→1 小时→1 天」的白名单设计是为**我们自己工具**生成的 TB 内规则链准备的;同事的归档不走 TB 规则(A3 ③ 原话「归档数据不依赖 TB 规则,只依赖遥测库做归档」)。两套归档并存的话,页面上会有两种「日电量」——需要在 A3 澄清时定谁是权威。

## 1. 逐条对照

### A1 · 告警规则写到哪里 ❓(需澄清)

| 同事原话(后端) | 解读 |
|---|---|
| 「告警规则:通过在资产配置告警模版 json,通过外部工具将 json 处理好,保存到 TB 对应资产」 | 他们现有做法:告警规则以 JSON 存在 TB 资产属性上,由**外部工具 / kz** 读取并判定,不是 TB 的 Device Profile 也不是规则链。生产库里的「告警设备清单」资产(ASSET Contains DEVICE)应该就是这套 |
| 「设备上报故障 – 状态……:直接在设备实例上配置」 | 设备自报故障位:在设备(实例)级配置,不进 Profile |
| 「两台设备……:规则链配置」「计算结果:规则链配置」 | 跨设备与依赖计算结果的告警:同意走规则链 |
| 未勾「同意分法」;未答「模板是否多项目共用」「已有手工规则有哪些」 | 对 Profile 路线既没同意也没反对,给的是第三条路 |

**我方回应**:
- 他给出的是**第三种告警引擎**(资产 JSON + 外部判定)。要先弄清:① 谁在判定——kz 定时扫还是 TB 规则链读 JSON?② 触发后告警落在哪——TB 的 Alarm 表(渲染器 `mode: 'alarm'` 能订到)还是 kz 自己的表?③ 这套 JSON 的格式是什么、有没有现成样例?
- 如果落点是 TB Alarm 表,渲染器不受影响,变化只在编译器:多一个「告警模板 JSON 编译目标」,可能比 Profile 路线更省事、也天然是站点级(资产级),泄漏风险为零。
- 如果落点在 kz 自己的表,`mode: 'alarm'` 就订不到,要走 `ext`。这是必须问清的。
- 「设备实例上配置」在 TB 里没有对应物(TB 告警规则只在 Profile 上),推测是指他们 JSON 里按设备写。待确认。
- **建议**:A1 暂不写 ADR 结论,约 30 分钟看一眼他们的告警 JSON 样例与判定代码入口,再定。我方 ADR-001 的「双轨」在他们的体系里可能变成「资产 JSON(站点级,主路线)+ Profile inactivity(通讯中断)」。

### A3 · 计算结果命名 🔁 + ❓

| 同事原话(后端) | 解读 |
|---|---|
| 「分类前缀问题,模糊匹配」「按分、5 分、时、日、月、年都是计算后值,不是原始值;前缀有业务匹配规则用途,改为 calc_ 原有的逻辑也要跟着变动」 | 他们的 key 前缀(如 `ts*` / `hist*` / `REALTIME_*` / `HIST_*`)被业务代码**模糊匹配**使用;给旧输出改 `calc_` 会破坏他们的匹配逻辑 |
| 「页面上分不清原始值和算出来的值:这是两部分数据……设备原始值在选定设备的遥测实时数据展示;归档数据在大屏展示」 | 他们靠「展示位置」区分原始 / 计算,不靠命名 |
| 「归档数据 – 不依赖 TB 规则,只依赖遥测库做归档」 | 他们的多级归档在 kz 里做,不经 TB 规则链 |
| 未答「其他再触发链路」「kz 回写要不要加前缀」 | 后者随 A4 失效 |

**我方回应**:
- 「老站点旧输出不改名」本来就是我方方案,与他一致。
- `calc_` 只对**我们工具新生成、写回 TB** 的量强制,不碰他们任何 key。但要确认一件事:他们的模糊匹配规则会不会把 `calc_` 开头的 key 误匹配进去(比如按 `*P*` 匹配功率)。**请他给一份前缀 / 匹配规则清单**,我们据此选一个不会撞的前缀(`calc_` 或改 `gx_`),写进 ADR-003。
- 级联白名单保留,但范围缩小为「我们工具自己生成的 TB 内多级汇聚」;他们的归档不受影响。
- 新问题(见 §0 第 3 点):同一站点「日电量」可能有两个来源——我们 TB 内 `calc_` 汇聚 vs 他们 kz 归档。**建议一期页面上凡是 ≥ 1 天粒度的统计量一律取 kz(`ext`),TB 内只做实时级汇聚(总功率、需量等)**,避免两套口径。这条要在 A3 澄清时一起定。

### A4 · kz 报表怎么上页面 🔁(改走路线 A,且为正式路线)

| 同事原话(后端) | 解读 |
|---|---|
| 「通过扩展服务的接口查询,通用接口可复用,回写不了,遥测库预计 3–7 天清除」 | 路线 B 不可行;kz 有通用查询接口可直接用 |

**我方回应**:
- **ADR-004 改为路线 A,不是过渡**:契约加 `{ mode: 'ext'; source: 'kz'; query: {...} }`,`DataSource.ext()` 由 tbClient 实现(包一层现有 `kzRevenueTrend` 那类调用),kz 地址作为 tbClient 配置项(宿主与单文件大屏都要配,这是代价)。

- **需要同事给**:kz 通用查询接口的路径、请求 / 响应格式、鉴权方式(现有 `stationRevenueTrend` 用任意 TB token,通用接口是否同样)、按设备 key 还是按站点 / 业务 id 查(现有 `businessIds.json` / `entityIds.json` 暗示有一层映射)。这决定 `ext.query` 的形状。
- `.env.example` 的 `KZ_BASE` 从「仅 ext 路线时需要」改为必配。
