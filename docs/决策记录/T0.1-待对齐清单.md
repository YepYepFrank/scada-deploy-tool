## A. 四个「怎么做」的决定(对应 ADR-001 ~ 004)

### A1 · 告警规则写到哪里?

**问题是什么**:现场人员在工具里配一条告警(比如「电压超过 250V 报警」),工具要把它写进 TB。TB 有两个地方可以放告警规则:
- **设备模板**(TB 里叫 Device Profile):写一次,这个模板下**所有设备、所有项目**都生效。
- **站点规则链**(TB 里叫 Rule Chain):只对这个站点生效,现有工具已经在用这条路。

**风险**:你们生产库里,一个「IED 设备模板」是多个项目共用的。如果 A 站点的电压阈值写进模板,B 站点的同类设备也会按 A 的阈值报警。

**我们希望的结果**:按一句话分——

> 「这条告警对该模板下的所有设备、所有站点都一样」→ 写设备模板;否则 → 写站点规则链。

一期具体分法:

| 写设备模板 | 写站点规则链 |
|---|---|
| 通讯中断 / 心跳超时 | 电压 / 电流 / 功率超限(阈值每个站点不一样) |
| 设备自己上报的故障位 | 「状态变了才报」这类 |
| | 要看两台设备一起判断的 |
| | 用到计算结果(`calc_` 开头)的 |

由工具按上表自动判断并显示「模板级 / 站点级」标签,现场人员不选。工具只改自己写进去的规则(带标记),你们手工配的规则一律不碰。

### A2 · 页面配置里怎么记录「这个卡片绑的是哪台设备」?

**问题是什么**:页面配置是一份 JSON 文件,里面每个卡片要写「读哪台设备的哪个量」。TB 里每台设备有一个 id(一长串字母数字),同一台设备在演示环境、镜像环境、正式环境的 id 都不一样。

**我们希望的结果**:
- 工具本地保存的项目文件里记**设备名字**(如 `PDR1_IED03`)。好处:同一份配置可以在镜像上调好再发到正式环境;文件可以进 git 看改动。
- 工具**发布**时把名字查成 id,写进 TB 的页面配置。
- **你的应用和渲染器只会看到 id**,不需要查名字。

发布时如果名字查不到、或者查到两台同名设备(名字加设备模板也分不开),发布会被拦住并列出清单,不会发出去一份半对的配置。

### A3 · 工具算出来的量怎么命名?会不会把现有的多级归档切断?

**问题是什么**:工具会生成一些计算结果(比如「5 分钟平均功率」「全站总功率」),这些结果也写回 TB 当作遥测。要防两件事:一是页面上分不清「设备上报的原始值」和「算出来的值」;二是算出来的值又触发一遍计算,形成死循环。

原来的方案是「算出来的值统一加前缀,凡是带前缀的一律不再触发计算」。但你们现有的多级归档(5 分钟 → 1 小时 → 1 天)和分层汇总,**正是靠「上一级结果再触发下一级」工作的**,一刀切会把它们切断。

**我们希望的结果**:
1. 工具**新**生成的结果一律加 `calc_` 前缀,工具界面上自动加、不能手改。
2. 老站点已经在用的结果量(如 `PAvg5m`)**不改名**,不动历史数据。工具只生成一份「建议改名清单」,一期不执行。
3. 多级归档 / 分层汇总走**白名单**:工具从配置里自动算出「哪些结果还要触发下一级」,只放行这些,其他带前缀的一律不再触发。白名单不需要人维护。

**需要你确认**:
- [ ] 同意
- [ ] 除了「分/时/天归档」和「4 分组 + 1 汇总」,你们还有没有别的「结果再触发计算」的链路?(有的话列出:______)
- [ ] kz 服务写回 TB 的数据(见 A4)要不要也加 `calc_` 前缀?我们建议加,统一当「算出来的值」看(同意 / 不同意)
