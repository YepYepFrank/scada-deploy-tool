**一期怎么做(写入 ADR-001)**:

- 他们的体系(资产 JSON + 规则链节点 + 告警设备清单)是生产可视化的现状,但这个「规则链节点」在镜像上不存在(镜像 3 条规则链里没有读资产 JSON 的节点),节点名、JSON 存在资产的哪个属性(KEY 清单里出现了 `alarm_config` / `alarm_devices` / `base_info`)也没给。
- 工具一期**继续用自己的站点告警规则链**(T1.3 已实现、parity 与 live 都过),Profile 不写。理由:不依赖一个镜像上没有、细节未知的节点;两套引擎同时写 TB 告警表会重复告警。
- 工具**增加一个导出**:把站点声明里的阈值告警导出成他们的 JSON 格式(`title / alarm_severity / operator / key / value` + 设备清单),供他们导入自己的体系或人工核对;默认不写 TB。二期再决定是否切到他们的引擎(届时删我们的告警链即可,发布器是幂等的)。
- 「值变了才报一次」「两台设备一起判断」他们支持,我们的规则链也支持(edge 触发 / 跨设备条件),语义对齐,不冲突。

**我方决定(写入 ADR-004 与契约 §4)**:

- 契约 `ExtQuery` 形状不变:`{ source: 'kz', window?, interval?, params }`。`params` 冻结为 `{ stationId?: string, deviceId?: string, keys?: string[], metric?: string }`,由 tbClient 映射到 kz 的请求体;`window` 由 tbClient 换算成毫秒 `startTime / endTime`;`interval` 的取值(`1m/5m/1h/1d/1M/1y`)到 kz 参数的映射表放在 tbClient 里,拿到 3.4 的答案后填。
- `ExtResult.series` 直接对应他们 `data` 里「量名 → 点列」的结构(`ts` / `value` 字段名一致,`createTime` / `zdValue` 忽略);统计类 key:value 结果(站点数、装机容量等,庄艳芹 4.7 提到)放 `ExtResult.meta`,组件按需读。
- 在拿到路径 / 粒度前,`LegacyDataSource.ext()` 只实现收益趋势(`stationRevenueTrend`,T3.8 已做),通用查询留空实现并报「kz 通用接口未配置」。

## 3. KEY 清单(xlsx)对我们的影响

- **不撞名**:他们的遥测 key 没有 `calc_`;资产名前缀 `XRS_ / GC_ / JIZHAN_ALL_`。我们的站点资产 `xrs-mirror-test`、汇聚资产 `RT_*_TEST`、页面资产 `ScadaPage` 类型都不在他们的命名空间里。
- **可以直接绑**:他们已在 TB 上算好的站点级量(如资产 `G42_HIGHWAY_XIANRENSHAN` 的 `totalConsumptionPower` / `totalGenerationPower`,`XRS_REALTIME_TOTAL_LOAD_POWER` 的 `tsLoadPowerTotal`)就是普通资产遥测,页面用 `ts` / `ts-history` 绑资产即可,不必再算一遍。里程碑 A 的「全站总功率」曲线可以改绑它们(待办 ② 的一个替代方案)。
- **一条预警**:清单里写了「移到网关设备,计算公式也从资产改到网关,后面对应的资产删掉;同时遥测命名要加前缀」——他们准备**删资产、改 key 名**。ADR-002 按名称解析只对「名字不变」有效;页面若绑了这些资产 / key,他们改名后发布时会报「解析不到」,校验层能抓到,但要提前知道时间表(§4)。
- 告警资产的属性名(`alarm_config` / `alarm_devices` / `base_info`)与 1.3 的 JSON 对上了,可作为二期「导出他们格式」的目标属性名,待确认。
