# 方案讨论:第三步保存即写 TB + 进入第三步前同步 · 2026-09-10

> 状态:**已讨论定案(2026-09-11),按 §9 实施**。YY 提需求,与同事讨论后定方案。
> 数据来自 2026-09-10 对镜像 TB(`192.168.20.61:8080`,CE 4.3.1.3)的只读普查,
> 复现一条命令:`node scripts/tb-rule-inventory.mjs`(加 `--root` 另列 Root 链全部节点)。

## 0. 需求原文(YY)

1. 第三步「保存并进入展示配置」点击后**直接写进 TB**(不加新按钮),这样第四步能拉到新建的结果资产和它的遥测。
2. 进入第三步之前做一次**同步**:读取 TB / kz 里已经配置过的所有计算、规则链,在第三步里显示出来,
   可以增删改查;点「保存并进入展示配置」后,把 TB / kz 内的配置**覆盖**成新的配置。
3. 部署工具配不了、需要在 TB / kz 里单独配的内容,要有同步的办法。

## 1. 结论

**两件事都能做,但「全部读进来、全部覆盖」这个版本不能做。** 可行的版本是:

- **只覆盖本工具管理的对象**;平台上别人配的计算字段、规则链一律**只读显示、不改不删**;
- 想让工具接手的,**逐条人工「接管」**;
- kz 目前读不到也写不了,要么等高潮加接口,要么维持分工。

理由见 §2 的现状:镜像上一半以上的计算字段和几乎全部规则逻辑都不是本工具建的,
而且 kz 的归档触发器就长在 Root 链里。

## 2. 镜像现状(2026-09-10 只读普查)

### 2.1 计算字段:80 个,全是 SIMPLE 类型

| | 数量 | 说明 |
|---|---|---|
| 对得上某站点当前声明 | 37 | 本工具发布的 |
| 对不上 | 43 | 多数是同事手配(全站实时曲线、运营简况、基站、站内概况等资产上的);也有**本工具早先发布、后来从声明里删掉的遗留**,如 `PDR1_LP1_IED1` 上的 `absQ` / `pqState` |

对不上的 43 个,表达式能不能套进向导的「自定义四则」模板(从左到右计算、每项可取绝对值):

| 判断 | 数量 | 例子 |
|---|---|---|
| 能套模板 | 30 | `a + b`(6 台 `PDR*` 设备的「总电压」)、`P141+P151+…` 求和、`total_energy/1000` |
| 纯常数 | 8 | 「主变容量」`10010`、「EV 装机容量」`3840`、「储能循环次数」`0` |
| abs 包住整个式子 | 5 | 「光伏实发功率」`abs(P111+P121+P131+411)`、「售电收益」`abs(total_energy*0.29)/10000` |

另一个障碍:向导里「计算字段名」和「输出测点名」是同一个名字,而同事的计算字段名多是中文描述
(如「实时曲线-负荷总功率-SSP1」→ 输出 `tsLoadPowerTotalSSP1`)。**43 个里有 32 个计算字段名 ≠ 输出测点名**,
即使表达式套得进,接管时也要先改数据模型。(每条的输出名见脚本输出。)

### 2.2 规则链:6 条,本工具的只有 2 条

| 链 | 节点 | 定时器 | 归属 |
|---|---|---|---|
| Root Rule Chain | 116 | 21 | 同事;**版本号已到 465**,改得很频繁。其中只有 1 个节点(`site alarms flow · xrs-mirror-test`)是本工具加的 |
| 基站储能规则链 | 34 | 2 | 同事 |
| Thermostat / 光伏发电电量报表规程链条 | 6 / 0 | — | 同事 |
| Site Alarms · xrs-mirror-test | 10 | — | 本工具 |
| Site Rollups · xrs-mirror-test | 30 | 4 | 本工具 |

**kz 的按分 / 5 分 / 时 / 天 / 月归档,是 Root 链上的定时器 + REST 调用节点触发的**
(「按分钟归档数据」→「按分归档」等)。也就是说 kz 的配置有一半在 TB 的 Root 链里。

### 2.3 kz

只有查询接口(`/kzserver/tskv/**` 通用历史、`/kzserver/biz/**` 业务统计),
**没有任何读写配置的接口**(见 `docs/联调记录/kz-接口实测-2026-09-07.md`)。

### 2.4 TB 实体上现成可用的两个字段

计算字段、规则链、资产上都有:

- `version`:乐观锁。保存时带上它,别人改过就返回冲突,而不是静默覆盖;
- `additionalInfo`:可以放「本工具建的、属于哪个站点」的归属标记。目前全是空的。

## 3. 需求一:第三步保存即写 TB

**可行。** 写入逻辑现成,就是把第五步 `publish` 里写规则的部分(计算字段、跨设备汇聚、分时收益、
定时统计链、告警链、站点配置)挪到「保存并进入展示配置」上;第五步只剩页面发布 + 规则自检。

要说清的一点:资产一建好,第四步就能选中它;但**遥测要等输入设备下一次上报、计算被触发后才有第一个值**
(一般几秒,设备不上报就一直是空的),定时统计要等满一个周期。第四步本来就能先绑「待发布」的测点
(`editor/declared-keys.ts`),所以真正缺的只是「资产存在」——这引出 §7 里的轻量替代方案。

## 4. 需求二:进入第三步前同步

| 来源 | 能否读进第三步增删改查 |
|---|---|
| 本工具建的 | **能**。现在连接时就会读站点资产的 `siteConfig` 回填(`loadSite` → `hydrate`) |
| 别人的计算字段 | **只能部分**,见 §2.1:30/43 表达式能套模板,且名字模型对不上 |
| 别人的规则链 | **不能**。任意节点图,向导的模板表达不了 |
| kz | **不能**,没有接口 |

## 5. 风险与逻辑漏洞

| # | 问题 | 后果 | 对策 |
|---|---|---|---|
| 1 | 「覆盖」不限范围 | 会删掉同事的 43 个计算字段、改掉 Root 链和 kz 归档触发 | 只覆盖本工具管的对象。但现在判断「是不是自己的」靠名字 + 上一版声明,**已经出过漏洞**:§2.1 那两个遗留字段工具认不出来,清不掉、还被当成别人的。要先在写入时往 `additionalInfo` 打归属标记 |
| 2 | 保存就等于上线 | 第三步是边改边存的地方,半成品立刻生效:告警链立刻开始建告警;删掉或改名一个输出,已发布页面上绑它的组件立刻失效 | 保存前列**影响清单**:增 / 改 / 删各几项、波及哪些已发布页面的哪些绑定,确认后才写 |
| 3 | 频繁保存让定时统计一直出不了数 | 每写一次规则链元数据,TB 重启链上所有节点,定时器从头计时。本工具的定时统计链有 4 个定时器,小时级要连续跑满 1 小时才出点,天级靠小时级驱动(`core/scripts.ts` 2026-09-09 的教训)。调试时十分钟存一次,小时 / 天归档就永远空 | **内容没变的链不写**(先比对再写)。这一条不管做不做需求一都该补——现在每次发布都在重写 |
| 4 | Root 链 | 告警从有变无、从无变有时,工具会把整条 116 节点的 Root 链读出、改完写回:①重启 Root 上 21 个定时器,**包括 kz 的天 / 月归档触发**,可能丢一天的日归档;②同事同时在改 Root 时,他的修改被覆盖 | 写 Root 带 `version`;转发节点一次接好、以后不摘(告警链为空时链内直通),把写 Root 降到一次 |
| 5 | 并发 / 丢失更新 | 进第三步时同步一份,保存时覆盖:两个人同时编辑同一站点,后保存的人整个抹掉前一个人的修改;有人在 TB 界面手改了工具建的对象,也被抹掉 | 同步时记下站点配置和各对象的 `version`,保存时比对,不一致就停下给出差异 |
| 6 | 只成功一部分 | 第三步保存有 9 个子步骤,比如一条计算撞上单实体上限 | 定规则:失败项列出可重试;能否进第四步;失败的输出在第四步标「未生效」 |
| 7 | 计算字段上限没算别人的 | TB 单实体最多 5 个。`PDR1_LP1_IED1` 已有 4 个(2 个是遗留),向导只数自己的,要到保存时才撞 | 同步时把各实体已占的名额一起读出来,弹窗里提前拦 |
| 8 | 权限 | 第五步有「现场账号只能发布授权站点」检查,第三步保存没有就能绕过 | 同一检查搬到第三步 |
| 9 | 发布历史被调试保存冲掉 | 站点资产只保留最近 10 版(`siteConfigHistory`),调试时存几次就把有意义的版本挤没了 | 区分「保存」和「发布版本」,只有后者进历史 |

## 6. 工具配不了、要在 TB / kz 单独配的内容,怎么同步

### 6.1 按对象分三类,三种待遇

| 类别 | 怎么认 | 第三步里 | 保存时 |
|---|---|---|---|
| 本工具管的 | 带归属标记 | 完整增删改查 | 覆盖 |
| 别人的 | 没有标记 | **只读列出**:计算字段显示所在设备 / 资产、表达式、输出名;规则链显示名字、节点数、定时器数。它们的输出照样出现在测点选择器里,可以引用、可以绑页面;占用的名额计入上限检查 | 不改不删 |
| 接管(可选) | 人工逐条点「接管」 | 表达式能套进模板的别人的计算字段,转成向导里的一条运算,保持原实体、原输出测点名(历史曲线接得上),打上标记 | 接管后才覆盖;提供「交还」去掉标记,工具不再管 |

### 6.2 四个配套办法

1. **漂移比对。** 同步时逐个比对工具管的对象「TB 上实际是什么」vs「声明是什么」,四种结果:
   - 一致;
   - 有人在 TB 里改过 → 三选一:以平台为准(能表示就写回声明)/ 以工具为准 / 这次跳过;
   - 被删了 → 保存时重建;
   - 声明里已经没有、但还带着标记(遗留)→ 三选一:删除 / 接管 / 交还。
2. **规则链留扩展点。** 同事要在工具的链路上加自定义逻辑时,不要改工具的链(下次保存会被覆盖)。
   工具在站点告警链、定时统计链末尾留一个节点,转发到 `Site Custom · <站点>`;这条链归同事手工维护,
   工具只保证接口在,永不改它。
3. **划清 Root 链的边界。** 工具在 Root 上只拥有自己那一个转发节点,其余节点只读;写 Root 时带 `version`,冲突就停。
4. **kz 两条路:**
   - 请高潮加**只读配置接口**(归档了哪些测点 / 站点、收益用哪个电价资产),向导只读展示——可作为
     `docs/给同事的-kz待改清单-2026-09-10.md` 的第 7 条;
   - 或维持现在的分工:kz 的配置由高潮负责,向导只在「外部数据」绑定里调它的查询接口。

   两条路下,kz 的归档触发器都在 Root 链上,所以 §5 第 4 条对 kz 同样要紧。

### 6.3 兜底

每次覆盖前,除了站点配置入历史,再把**工具管的对象在 TB 上的实际样子**(计算字段 JSON、规则链元数据)存一份快照,
出问题一键回滚到保存前。

## 7. 建议的做法和顺序

| 阶段 | 内容 | 说明 |
|---|---|---|
| ① 底线 | 未变不写;写入带 `version`;写入时打归属标记 | 不管做不做需求一都该先有 |
| ② 需求一 | 第三步保存写 TB + 影响清单确认 + 权限检查 + 「保存 / 发布版本」分开 | |
| ③ 需求二(只读) | 同步时列出别人的计算字段与规则链、已占名额;比对工具自己对象的漂移 | |
| ④ 接管 / 交还 | 别人的计算字段逐条接管;名字模型要先支持「计算字段名 ≠ 输出名」 | |
| ⑤ kz | 等高潮出只读配置接口 | 可选 |

**更轻的替代(只为解决「第四步选不到结果资产」):** 第三步保存**只建结果资产和挂到站点下的关系**,
计算字段和规则链仍在第五步写。风险小得多(不建告警、不动规则链、不重启任何定时器),
代价是第四步看到的资产上暂时没有遥测(绑定照样能先选「待发布」的测点)。

### 9.1 kz 接口文档里有什么(《TB-kz汇总业务-接口_20260818002.docx》)

- **查询类**:`tskv/{minute,minutefive,hour,day,month,year}`(通用历史)、`biz/power/*`(收益、电量、利用率、站点详情、实时曲线等)、报表下载。
- **有增删改的全是业务配置**:峰谷套利方案 `biz/plan/*`、配置策略 `biz/planstation/*`(方案下发到哪个站点、何时生效)、
  时控方案 `monitor/job/*`(开关灯这类定时控制)、OTA `biz/tbota/*`。
- **没有任何「计算 / 归档 / 规则」相关的配置接口**——归档口径写在 kz 代码里。
- 归档是 Root 链上 5 个 REST 节点定时调 `:8099/rulestaticsapi/{minute,minutefive,hour,day,month}` 触发的,
  **这组接口不在文档里**(镜像普查所得)。
- 所以第 3 步没有 kz 的东西可同步。以后若要在向导里看 kz 的配置,请高潮加只读接口(可并入 kz 待改清单)。

### 9.2 实施要点

- **归属标记**:`additionalInfo: { managedBy: 'deploy-tool', site }`(与页面资产同一个 `managedBy`),打在计算字段、
  工具建的资产、新建的规则链上。清理旧输出只删「带本站点标记」或「上一版声明过、且不是接管来」的字段。
- **不覆盖别人的修改**:更新计算字段带 `version`;TB 回 409 时报
  「刚被别人改过(版本冲突),这次没有写入、也没有覆盖对方的修改」。Root 链上只动本站点自己的转发节点,写前核对别人的部分一字不差、带 version(见上表第 5 行)。
- **规则链内容没变就不写**;发布后自检只查真正重写过的链。
- **第 3 步保存**(`ensureResultAssets`):建结果资产(`tbsite-agg`,带标记)、站点资产、`Contains` 关系,Customer 跟站点走;
  同名的非本工具资产记冲突、不借用,停在第 3 步让人换名;建完第 4 步编辑器自动重读实体树。不建计算字段、不动规则链。
- **进第 3 步自动同步**(`readPlatformState`,只读):
  本工具管的(一致 / 平台上被改过 / 带标记但声明里已没有)、声明里有但平台上还没有、别人的(可接管 / 只读 + 原因)、
  别的站点的、规则链清单;每个实体已占的计算字段数(含别人的)用来在弹窗里提前拦单实体上限。
- **接管**(`core/adopt.ts`):只接能用「设备遥测 + 从左到右四则」等价表示的 SIMPLE 字段,翻完用随机数核对等价;
  保持原实体、原字段名、原输出名(不加 `calc_`),第 5 步发布时原地更新并打标记。
  **交还**:去掉标记、字段原样留着,之后发布与清理都不删它。
- **暂不做**:「以平台为准」把平台上被改过的字段反向导入(现在提示「第 5 步发布会以向导为准覆盖」)。

### 9.3 顺带发现(请同事确认)

两个同事手配的字段疑似笔误——参数定义了,表达式里却写成了常数:

| 字段 | 参数 | 表达式 |
|---|---|---|
| 实时曲线-负荷总功率-SSP1 | P141、P151、P161、P171、P191 | `P141+151+161+171+191`(结果是 P141 + 674) |
| 新能源光伏发电实发功率计算 | P111、P121、P131、P411 | `abs(P111+P121+P131+411)` |

**2026-09-11 已修正**(YY 定):两条都在镜像上补上了 P——`P141+P151+P161+P171+P191`、`abs(P111+P121+P131+P411)`;
只改表达式、带版本号写回、不打工具标记(字段仍归同事)。改后核对:SSP1 新值 183.33 = 5 个参数最新值之和;
光伏新值 11780 ≈ 按参数算的 11779.83。依赖它们的汇总(如 `tsLoadPowerTotal`)数值会随之变化——这是更正,不是故障。
