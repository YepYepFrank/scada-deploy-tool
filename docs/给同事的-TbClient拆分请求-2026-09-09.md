## 2. 现在卡在哪(比我原先以为的小得多)

**你的 `TbClient` 本身已经是可注入的了。** `useInjectedFetch` 那个开关做得很干净:
传了 `fetchImpl` 就整个走标准 fetch/Response,一致性套件就是这么跑的。

真正卡住我们的只有 `src/services/tbClient.js` **文件头那三行**:

```js
import request from '@/core/request'
import { getApiRequestUrl } from '@/core/runtime'
import { getKzTimeseriesValue, stationRevenueTrend } from '@/services/thirdApi'
```

`@/` 是你工程的别名,我们的仓库解析不了,所以这个文件我们 import 不进来——**是模块
解析的问题,不是逻辑耦合的问题**。改成动态 `await import()` 也没用,打包器在构建期
一样要解析这个路径。

这三个模块在类里一共只有四处用到,而且全都在「非注入」分支里:

| 位置 | 用到 | 什么时候才会走 |
|---|---|---|
| 第 72 行 `appApiRoot()` | `getApiRequestUrl` | 只在第 559 行拼 WS 地址、且 `options.wsUrl` 和 `options.baseUrl` 都没给时兜底 |
| 第 455 行 `request.get(toAppRequestPath(path))` | `request` | `!useInjectedFetch` |
| 第 389 行 `getKzTimeseriesValue(...)` | `thirdApi` | `!useInjectedFetch` |
| 第 429 行 `stationRevenueTrend(...)` | `thirdApi` | `!useInjectedFetch` |

也就是说:只要我们传了 `baseUrl` + `fetchImpl` + `kzBaseUrl`,这三个模块**一次都不会被
调用**——它们只是被 import 进来了而已。

## 3. 想请你做的:拆成两个文件

核心不带任何 `@/` 引用,应用相关的东西全部从 options 进来;你的应用再套一层薄封装,
把现在那四处默认行为原样传进去。**你的页面代码一行都不用改,运行时行为也不变。**

```
src/services/
  tbClient.core.js   ← 现在这个类,去掉三行 import;新增四个可选钩子
  tbClient.js        ← 薄封装:import 那三个模块,构造 core 并把钩子传进去,default export 保持不变
```

核心新增的可选项(名字随你,能对上就行):

```js
// tbClient.core.js
export class TbClient {
  constructor(options = {}) {
    // …现有的 getToken / fetchImpl / WebSocketImpl / baseUrl / kzBaseUrl 都不动…
    this.restImpl         = options.restImpl          // 替代 request.get(toAppRequestPath(path))
    this.kzTimeseriesImpl = options.kzTimeseriesImpl  // 替代 getKzTimeseriesValue(...)
    this.kzRevenueImpl    = options.kzRevenueImpl     // 替代 stationRevenueTrend(...)
    // WS 地址:core 里不再兜底到 appApiRoot(),由封装传 wsUrl 或 baseUrl
  }

  async rest(path) {
    if (this.restImpl) return this.restImpl(path)     // 应用:走 request.js 的 token/401 处理
    /* …现有的标准 fetch 分支原样保留… */
  }
}
```

```js
// tbClient.js —— 你的应用继续 import 这个,行为和现在完全一样
import request from '@/core/request'
import { getApiRequestUrl } from '@/core/runtime'
import { getKzTimeseriesValue, stationRevenueTrend } from '@/services/thirdApi'
import { TbClient as Core } from './tbClient.core'

const appApiRoot = () => String(getApiRequestUrl() || '').replace(/\/+$/, '').replace(/\/api$/, '')
const toAppRequestPath = (p) => p.replace(/^\/api(?=\/|$)/, '') || '/'

export class TbClient extends Core {
  constructor(options = {}) {
    super({
      wsUrl: options.wsUrl || options.baseUrl || appApiRoot(),
      restImpl: (path) => request.get(toAppRequestPath(path)),   // 含你现有的错误码转换
      kzTimeseriesImpl: getKzTimeseriesValue,
      kzRevenueImpl: ({ queryType, stationId }) => stationRevenueTrend({ queryType, stationId }),
      ...options
    })
  }
}
export default TbClient
```

`useInjectedFetch` 这个判断可以顺势简化成「有没有给 `restImpl`」,不过怎么写你定,
只要**一致性套件还是 15/15** 就行——那套用例就是我们双方的验收标准,别的都好商量。

## 4. 有一件事要你拿主意:核心文件放哪

拆完之后,`tbClient.core.js` 有两个去处:

**① 留在你的仓库,发包给我们。** 你现在怎么维护还怎么维护。代价是要新建一条
「你 → 我们」的发包流程。说实话我们对这条路有点怵:09-06 我们给你那个 tarball 没附
提交号,结果你手上的包比契约旧了一版,`ext` 的 kz 通用历史那条用例白白卡了一天。
反方向大概率会重演同一个问题。

**② 挪进 `@grid/tb-client`(我们更倾向这个)。** 核心文件放到我们包里,和契约、
一致性套件放在一起;你的应用照旧 `import { TbClient } from '@grid/tb-client'`,再套你的
薄封装。好处是**只有一条发包流程(我们 → 你),就是现在这条**,而且实现和它的验收
用例永远在同一个仓库里、同一个提交里,不会再出现版本对不上。

② 等于把 09-06 第二轮回填时「TbClient 留在你的应用仓库」那个约定改回来一半——**当时
那个约定是有道理的**(你要能自由改自己的客户端),所以这事得你同意,我们不会单方面
定。如果你更想保留对这个文件的所有权,选 ① 我们也接受,只是发包时请务必附上提交号。

不管选哪个,**薄封装那一层永远在你的仓库**,你的应用怎么接 request.js、怎么处理 401,
都还是你说了算。
