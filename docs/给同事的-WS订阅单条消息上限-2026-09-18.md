# TB WebSocket 订阅:单条消息不能超过 32 KB(给庄艳芹 / 高潮)· 2026-09-18

一句话:**一次往 TB 的遥测 WebSocket 里发的订阅命令,单条消息超过 32 KB,TB 会直接把连接关掉(关闭码 1009),一条数据都不回。** 现在的页面只有几十个测点,碰不到;我们接下来要做的一次接线图一张图有 300–400 个测点,一定会碰到。你们自己的 TbClient 如果也是「把一批订阅合成一条消息发」,需要同样处理。

## 实测(新后端 192.168.20.60,TB CE 4.3.1,只读)

| 做法 | 单条消息大小 | 结果 |
|---|---|---|
| 一条消息 230 个订阅 | 28.7 KB | 正常 |
| 一条消息 300 个订阅 | 37.4 KB | 连接被关,`1009 The decoded text message was too big for the output buffer…` |
| 一条消息 400 个订阅 | 49.9 KB | 同上 |
| 400 个订阅拆成 3 条消息(每条 ≤ 24 KB) | 23.9 KB | 正常,400 个都有回推 |
| 400 个测点按设备合并成 67 个订阅(一台设备一条,`keys` 用逗号拼) | 9.3 KB | 正常 |

上限是 TB 配置 `server.ws.max_text_message_buffer_size`,缺省 32768 字节,两台环境都是缺省值。一个订阅命令(36 位 id + scope + cmdId + 一个 key)大约 125 字节,所以**约 260 个订阅**就到顶。

还有一个连带问题:被关掉以后如果客户端自动重连并把全部订阅原样重发,会**断开 → 重连 → 再断开**一直循环。

## 建议的处理(两条都做)

1. **按实体合并**:同一台设备 / 资产的多个 key 合成一条订阅命令(`keys: "P,Q,Ia,Ib"`)。订阅数从「测点数」降到「设备数」,是主要手段。回推的数据里本来就按 key 分开,拆回去不难。
2. **分片发送**:合并后仍可能很大(设备很多的页面),发之前按大小切,单条消息控制在 24 KB 以内,连续发几条即可,TB 不要求一条发完。**重连后的重发也要走同一个分片逻辑。**

我们这边的 `LegacyDataSource`(`packages/tb-client`)会按这两条改,任务号 T5.4。

## 需要你们确认的

- 庄艳芹:你那边正式的 TbClient 订阅是怎么发的?如果是逐条发(一个订阅一条消息)就不受影响;如果是合并发,请按上面处理。
- 高潮:不需要改 TB 配置。调大 `max_text_message_buffer_size` 也能绕过,但那是每个部署环境都要记得改的一处配置,我们不打算依赖它。
