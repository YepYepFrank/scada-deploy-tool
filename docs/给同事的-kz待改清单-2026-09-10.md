## 1. `tskv/**` 按实体归属过滤(上线前必须)

**现在**:token 真假已经会校验,但**不看这个 token 有没有权限访问路径里的那个实体**。
客户账号去读一台**没分配给它**的设备,TB 回 403,kz 照样把数据给出来,点数和租户账号拿到的一模一样:

| 设备(客户账号未分配) | TB 同一 token 读设备 | kz 租户 token | kz 客户 token |
|---|---|---|---|
| `Test Device A1` | 403 | 200 · 7 点 | **200 · 7 点** |
| `Test Device A2` | 403 | 200 · 7 点 | **200 · 7 点** |
| `RY_GZ_ESS_PCS`(润扬) | 403 | 200 · 7 点 | **200 · 7 点** |

直连 `:8099/kzserver` 和经 nginx 反代 `/kz/kzserver` 两条路结果一样(09-10 复测)。

**后果**:任何一个能登录的客户账号,都能读到整个库所有设备的归档。一期所有客户账号都属同一个项目客户,
所以眼下没有实际损失;但生产上是**一站一个客户**,那时仙人山的账号就能读润扬的全部历史。

**建议改法**(两种都行,你按 kz 的结构选):

- **A. 问 TB**:`tskv` 拦截器里,拿请求的同一个 token 调一次 TB 的 `GET /api/device/{id}`
  (资产用 `/api/asset/{id}`),非 2xx 就拒。可以按 `(token, entityId)` 缓存 1 分钟,免得每个请求都打 TB。
  好处是跟 TB 的判定永远一致,以后 TB 改分配关系 kz 不用跟着改。
- **B. 自己查**:从 token 里取 `customerId`,在库里查这个实体的 `customer_id` 是否一致。
  更快,但要自己处理「租户账号放行」「Public 客户」这些边界。

**拒的时候请回明确的错**(见第 3 条),比如 `code 403 无权访问该实体`,不要回 `code 200` + 空数据。

**我们怎么验**:仓库里有现成脚本,一条命令:

```bash
node scripts/kz-ownership-check.mjs
```

改好后,上面三台未分配设备应该都显示 **「✅ 拦住了」**(租户有数据、客户被拒);本客户的
`SSP1_GP1_IED1` 两个 token 都应该照常有数据。我们这边的自动化用例 `kz-auth.live.ts` 里那条
`it.todo` 到时候转成真用例常跑。

**在它修好之前**:现场 8099 不要对客户可达的网络开放,只走同机 nginx 反代(反代层已经会先拿 token 去 TB
验一次,挡住了「没登录的人」,但挡不住「登录了、但不该看这台设备的人」——这一层只能 kz 自己做)。

## 2. `biz/**` 按站点归属过滤(上线前必须 · 09-10 新发现)

**现在**:收益趋势 `POST /kzserver/biz/power/stationRevenueTrend` 也一样,不看 `stationId` 是不是这个客户的:

| 站点(网关设备) | TB 同一 token 读设备 | 本年逐月 · 租户 | 本年逐月 · 客户 |
|---|---|---|---|
| `bs_1_ems`(本客户) | 200 | code 200 · 1 行 | code 200 · 1 行 |
| `bs_2_ems`(**未分配**) | **403** | code 200 · 1 行 | **code 200 · 1 行** |

客户账号能看到不属于它的站点的收益。改法与第 1 条相同:对 `stationId`(就是 TB 里 `gateway` 类型设备的 id)
用同一 token 问一次 TB `GET /api/device/{stationId}`,非 2xx 就拒。

`/biz/power/*` 下其它业务统计接口(`statPowerRevenue*`、`statPowerVolume*`、`stationRealP`、
`todayPowerVolume/{stationId}` 等)如果也带站点 id,请一并按这个处理——**最好做成一个拦截器统一管**,
新接口自动带上,不用每个控制器各写一遍。

**我们怎么验**:同上,`node scripts/kz-ownership-check.mjs` 末尾会列收益趋势这一段(09-10 已加进去),
`bs_2_ems` 的客户那一栏应变成被拒。

## 3. 错误要分得清(建议)

现场排障时最怕「看起来是没数据,其实是别的原因」。现在有四种情况的回法和「没数据」撞了:

| 情况 | 现在回 | 希望回 |
|---|---|---|
| 客户读未分配的实体(第 1、2 条修好后) | —— | `code 403` + 「无权访问该实体」 |
| 收益趋势传了**不是站点**的 id(普通设备、编的 UUID、`xrs_fileserver`) | `code 500 该站点下无设备` | `code 404`(或 400)+「不是站点(网关)设备」 |
| 收益趋势传的是站点,但这个站点**真没归档** | `code 500 该站点下无设备`(部分站点)/ `code 200` 0 行 | `code 200` + 空数组(统一成这个) |
| `agg` 传了不支持的值(如 `SUM`) | `code 200` + `data: {}`,**静默为空** | `code 400` +「不支持的聚合方式,只支持 AVG / MAX / MIN / ZD」 |

另有一条小的:多个 key 里有一个不存在,现在整个请求失败(`code 500 key不存在`)。能的话把存在的照常返回、
在 `msg` 里列出不存在的 key;做不到也没关系,我们的编辑器在绑定时已经先查过 key。

HTTP 状态码一直是 200、真正的结果在 `code` 里——**这个不用改**,我们已经按这个写了。

## 4. 加一个版本接口(建议,很省事)

09-10 有人说「归属过滤已经修了」,我们测下来镜像上没修——但**没法从 kz 本身看出它跑的是哪个包**,
只能去容器里对 jar 的 md5。建议加一个不需要登录的接口,例如:

```
GET /kzserver/version
→ { "version": "1.x.x", "commit": "abc1234", "buildTime": "2026-09-10T08:00:00+08:00" }
```

Spring Boot 开 actuator 的 `info` 端点、配上 `git-commit-id` 插件就有,几乎零代码。以后每次给新包也请附上
md5 和一句改了什么——我们给同事的前端包从 09-10 起也这么做了(文件名带提交号 + 包内 `build-info.json`)。

## 5. 接口文档与实际行为对齐(不急,只改文档)

`TB汇总业务-接口_20260818002.docx` 里有三处和实际跑出来的不一样。我们已经按实际行为写好了,**代码不用改**,
把文档改对即可,免得后来的人照文档踩坑:

| 项 | 文档写 | 实际 |
|---|---|---|
| `interval` 参数 | 统计单位,毫秒 | **被忽略**,粒度只由路径段(`minute / minutefive / hour / day / month / year`)决定 |
| `year` 桶 | —— | 只回 1 个点,`ts` 是**查询时刻**,值是当年到现在的聚合(若方便,`ts` 改成当年 1 月 1 日 0 点会和 `month` 桶一致,可选) |
| `zdValue` | 非 ZD 时为 null | 非 ZD 时是 **0** |

另外两条文档里没写、建议补上的:返回点**升序**;缺数据的时段**不补点**(直接缺,不是补 0)。
