# kz 通用历史接口实测 · 2026-09-07

> 目的:第三轮回填给的接口文档(`决策记录/Other/TB汇总业务-接口_20260818002.docx`「服务端扩展业务 HTTP 协议接口」)在镜像 kz(`http://192.168.20.61:8099`)上逐桶打一遍,核对返回形状、粒度参数、ZD 语义与错误路径;`LegacyDataSource.ext()` 的通用历史分支照此定稿,并落成 live 用例 `packages/tb-client/test/live/kz-ext.live.ts`(`pnpm -F @grid/tb-client test:live`,7/7 通过)。
> 探测对象:`SSP1_GP1_IED1`(DEVICE)、`xrs-mirror-test-agg`(ASSET,昨晚工具产出的 `calc_totalP`);用租户 token。

## 1. 结论

| 项 | 文档说法 | 实测 | 对我们的影响 |
|---|---|---|---|
| 六个粒度桶 | 路径段 `minute / minutefive / hour / day / month / year` | 全部 200,数据升序,步长分别 60 s / 300 s / 1 h / 1 d / 月初 / 单点 | `KZ_BUCKETS` 映射正确 |
| `interval` 参数 | 「统计单位,毫秒」 | **被忽略**:`minutefive` 传 `interval=60000` 仍回 5 分钟步长;`month` 传 30 天或 0 结果一样;`year` 传 366 天或 0 一样 | 粒度只由路径决定;tbClient 照文档填毫秒即可,填错也不影响 |
| `zdValue` | 「非 ZD 时 null」 | 非 ZD 时是 **0**,不是 null;`agg=ZD` 时 `value === zdValue` | 我们只读 `value`,不受影响 |
| 返回顺序 | 未说明 | 升序 | 适配器仍排一次序,幂等 |
| 缺数据的时段 | 未说明 | **不补 0,直接缺点**:天桶 30 天只回 4 个点(归档 09-02 起),小时桶有 17 h 空洞(09-05 镜像停机) | 曲线组件按 ts 画,自然断开;不要假设等距 |
| `month` 桶 | — | 点落在每月 1 日 00:00(东八区);没数据的月 `value: 0, zdValue: null` | 月柱图前端可把 0 视为无数据 |
| `year` 桶 | — | **只回 1 个点,`ts` = 查询时刻**(`createTime` 就是当前时间),值是当年到现在的聚合 | 年级别不适合画曲线,适合做数字卡;live 用例已固化这一怪癖 |
| 不存在的 key | 未说明 | HTTP **200** + `{ code: 500, msg: "key不存在" }`;多 key 里有一个不存在则整个请求失败 | `ext()` 按 `code ≠ 200` 抛「key不存在」;页面绑定前校验层已按 key 存在性拦一道 |
| 不支持的 agg(SUM) | 「支持 AVG / MAX / MIN / ZD」 | HTTP 200 + `code 200`,`data: {}`(**静默为空**) | 适配器只放行四种,其它回落 AVG |
| 资产上的 key | — | `calc_totalP` 发布 14 小时后已在 minute / minutefive 桶里,归档自动收新 key | ADR-003「遥测归档、属性不归档」实证 |
| 首次调用耗时 | — | 冷启动 5.6 s,之后 20–90 ms | 页面首屏 ext 组件要有加载态(渲染器已有) |
| **鉴权** | 「X-Authorization:TB 登录 token」 | **分路径**:`biz/**` 正常(无 token → `code 500 token不能为空`,假 token → `code 401 token失效`);`tskv/**` 只判非空——`Bearer nope`、篡改签名的 JWT、`exp=2001` 的过期 JWT、客户 token 读未分配的润扬设备,全部 `code 200` + 完整数据(09-07 13:5x 复核,每次换窗口排除缓存) | **`tskv/**` 少挂了鉴权拦截器**,见 §3 |

## 3. 需要同事(高潮)处理的一条:kz 的 token 校验

**复核结论(09-07 13:5x,`kz-auth-probe`,每次请求换时间窗口排除响应缓存):不是误报,但范围比初判窄——只有 `/kzserver/tskv/**`(通用历史六个桶)不校验;`/kzserver/biz/**` 校验正常。** 具体:

| 请求 | `tskv/minute/…` | `biz/power/stationRevenueTrend` · `biz/tb/menu` |
|---|---|---|
| 有效租户 token | 200 数据 | 200 数据 |
| 无 / 空 header | `code 500 token不能为空` | `code 500 token不能为空` |
| `Bearer nope`(非 JWT) | **200 数据** | `code 401 token失效` |
| 篡改 payload + 假签名的 JWT | **200 数据** | — |
| 过期 JWT(exp=2001,原签名) | **200 数据** | — |
| token 放 `Authorization` 头 | `token不能为空`(只认 X-) | — |
| 客户 token 读未分配的润扬设备(TB 侧 403) | **200 数据** | — |

推断:kz 的鉴权拦截器(向 TB 核实 token)只挂在 `biz/**` 路径,`tskv/**` 控制器漏挂,且 `tskv` 没有按 token 身份做实体归属过滤。后果:

- 拿到 kz 地址的任何人都能读全库归档(所有站点、所有 key),与 TB 侧的 Customer 隔离脱节;
- 我们在 ADR-004 里假定「kz 与 TB 同 token、同权限」,这条现在不成立。

建议:把 `biz/**` 已有的 token 校验拦截器同样挂到 `tskv/**`(一行路径配置的事);客户账号进一步按 TB 的实体归属过滤(TB 对未分配实体回 403,kz 可同样查一次 `/api/{type}/{id}` 透传)。**在这之前,现场部署 kz 不要暴露在客户可达的网络上,只走同机反代且反代层先过 TB 鉴权。** 已列入 `docs/联调环境.md` §5 待办 ⑤ 与 `给同事的开发说明.md` §4。
