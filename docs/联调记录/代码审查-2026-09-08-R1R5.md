## R1 · 发布时清理声明里已删除的旧链 —— 已关闭(2026-09-08)

**改动**:`writer/publish.ts`

- 提取 `unwireRootChain(api, siteName)`,把 Root 上摘节点与连线索引重排的逻辑集中到一处;`cleanup.ts` 改为复用它,不再各留一份。

- 结果拼进各步骤的报告行,例如 `alarm:ok 无(已删上一版的 Site Alarms · S,已摘除 Root 转发)`。
- 清理失败不阻塞本次写入,记一条 failure。

**只删两类名字,都是我们自己建的**:

1. 本站点的默认链名(`Site Alarms · <站点>` 等)—— 这样早就孤立的旧链也能收拾掉;
2. 上一版已发布配置声明过的链名 —— 覆盖自定义 `chainName` 与改名场景。

仍在本次声明里的链名进 `keep` 集合,任何情况下不删。除这两类之外一律不碰,避免误删同事的链。

## R4 · 迁移中断重试 —— 已关闭(2026-09-08)

**改动**:`writer/migrate.ts` + `bin/tbsite.ts`

1. **上界钉住**:新增 `cutover` 选项与 `cutoverKey(row)`。CLI 每次 `--apply` 后把本轮算出的上界写进 `migrations/<站点>.migrate-state.json`,下次自动带上。
2. **删之前核对**(只读,两段都要过):上界之前新 key 点数不少于旧 key;上界之后的重叠段,新 key 点数也不少于旧 key。上界被带偏时后一条必然不过。**重叠段本身是设计允许的**(新旧 key 并行写过一阵,重叠段以新 key 为准不复制),所以不能简单地「上界之后还有旧点就算不完整」——第一版规则就是这么写的,被既有用例挡下来了。
3. **逐行容错**:一行出错记 `error` 不抛出,不影响其它行,出错的行绝不走到删除。
4. CLI:核对没过或有行出错则退出 1,并打印每行原因。

**回归证据**

- 单测 6 条(`test/drift-migrate.test.ts`):写到一半失败 → 记 error、旧 key 一点没删;中断后**不带**上界重试 → 上界缩到已搬进去的第一个点、核对拦住、旧数据保住、报告点名原因;中断后**带**上界重试 → 补齐余下历史、核对通过才删、一个点没丢;重叠段正常场景仍放行;一行出错不影响其它行;`cutoverKey` 的区分度。顺带把内存 TB 的写入改成按 ts 覆盖(真实 TB 的语义),否则重跑会留重复点。
- 真实 CLI + 镜像实跑(临时资产承载数据,做完即删):
  - 完整迁移 → `已删旧 key r4_old 的数据(核对:旧 3 点已在新 key)`,新 key 四点齐全,状态文件写入上界,退出 0。
  - 新 key 有缺口(等价于上界被带偏)→ `上界 … 之后旧 3 点、新 key 只有 2 点 … 不删旧 key`,旧数据三点完好,退出 1。
- 全量:compiler 94、tb-client 19、renderer 45、deploy-tool 53,类型检查与格式检查通过。

**遗留**:重试是重跑整个区间而不是断点续传(写入按 ts 覆盖,幂等)。大表重试会多花一次复制时间,换来实现简单、不必维护断点游标。

## R2 / R5 · Customer 取消分配 —— 已关闭(2026-09-08)

两条是同一个缺口的两面,一起改。

**共同根因**:TB 用占位 UUID 表示「未分配」,它是非空字符串。`followSiteAsset` 直接拿 `customerId.id` 当真客户用(R5);`publishPage` 虽然认得这个占位值,却只在「站点无客户」时打了条成功日志,没对已有归属的页面做取消(R2)。

**改动**

- `core/constants.ts` 新增 `NULL_UUID` 与 `customerIdOf(entity)`(未分配归一成 `null`),常量从 `page/publish-page.ts` 迁过来并保留原路径转出;两处读 `customerId` 的地方都改走它。
- 归属始终跟着站点走,补齐「有→无」这一格:页面用 `DELETE /api/customer/asset/<id>`,回滚项是改回原 Customer;汇聚 / 收益资产同样处理。
- 取消分配只在目标资产确实有归属时才调 —— 真实 TB 对「本来就没分配」再取消一次回 **400**(镜像实测),两个 mock 都按这个行为写了,谁去掉判断都会被测试挡下。

**回归证据**

- 单测 R2 五条(`test/publish-page.test.ts`):站点取消分配 → 页面同步取消并发出 DELETE、日志说明;站点换客户 → 页面跟着换;两边都未分配 → 一个 customer 请求都不发;已一致 → 不重复分配;取消分配这一步失败 → 归属保持原样、不留半吊子状态。
- 单测 R5 三条(`test/writer.test.ts`):站点未分配 → 不向占位 UUID 发分配请求(老代码在这里 404 并把 asset 步骤判失败);站点取消分配而汇聚资产还挂着 → 汇聚资产同步取消;有客户 / 换客户 / 已一致三种情况分别正确。
- 镜像实测:占位 UUID 分配 → `404 Customer with id [13814000-…] is not found`;`DELETE /api/customer/asset/{id}` → 200 且归属变回未分配;已未分配时再调 → 400。临时资产用完即删。
- 全量:compiler 102、tb-client 19、renderer 45、deploy-tool 53,类型检查与格式检查通过。

**遗留**:站点资产本身的归属由人在 TB 里改,工具不代管;工具只保证页面与汇聚资产跟随它。

## R3 · 历史曲线绑定的多测点 —— 已关闭(2026-09-08)

**契约澄清**:渲染器按**绑定条数**出序列(`list.map` 出 `SeriesValue`),折线组件的 `series` 槽位是 `multiple: true`。所以「一条绑定 = 一条序列 = 一个测点」,多条曲线用多条绑定。早期编辑器却在**一条绑定内部**提供了「+ 再加一个测点」,多出来的测点被解析器 `keys[0]` 静默丢掉。

**改动**(三处一起,让这种配置既造不出来、也发不出去、还不会悄悄丢数据)

1. **编辑器**(`BindingRow.vue`):去掉「+ 再加一个测点」,只留一个测点选择器。遇到早期配置留下的多测点,原样提示并给两个出口——「拆成 N 条绑定」(`BindingsPanel.splitAt`,窗口 / 聚合等字段照抄,不用重配)和「只留第一个」。改第一个测点时**保留**多余项,免得「改个 key」把它们又悄悄抹掉。
2. **校验层**(`validate.ts`):多测点 → error,顶栏「不可发布」、发布按钮禁用。规则放在**不连 TB 也跑**的静态层(第一版误放在需要连接的绑定层,离线时不生效,浏览器里查出来后移正)。
3. **渲染器**(`binding-resolver.ts`):仍按第一个测点渲染(不让历史页面整块报错),但打一条点名 `组件/槽位`、列出被忽略测点、给出正确做法的 `console.warn`。

**回归证据**

- 单测 4 条:渲染器多 key → 警告一条且仍出一条序列;校验层 → error(单测点不报);`BindingRow` 单测点无「再加一个」也无提示、多测点显示两个按钮并正确 emit;`BindingsPanel` 拆分 → 三条绑定各一个测点、窗口与聚合照抄。既有两条建立在旧行为上的用例已按新契约改写。
- 浏览器实测(编辑器 5173):灌入三测点绑定 → 只有一个选择器、「+ 再加一个测点」已消失、提示显示「Q、Ua」;点「拆成 3 条绑定」→ 面板变三条、各一个测点、窗口聚合都是 24h/AVG、提示消失;灌入两测点 → 校验区列出「注册表 line-g1/series …」、顶栏「1 个错误,不可发布」、发布按钮禁用。
- **存量排查**:扫了本地页面目录与镜像上 3 张已发布页面,**没有任何多测点绑定**,新校验不会挡住现有页面。
- 全量:compiler 102、tb-client 19、renderer 46、deploy-tool 55,类型检查与格式检查通过。

**遗留**:契约的 `keys` 仍是数组(schema 没收紧成 maxItems 1)——一期契约已冻结,靠编辑器与校验层拦住;二期随契约修订再收。
