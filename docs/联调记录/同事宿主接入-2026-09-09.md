## 2. 第一版的缺口与她的修复(kz 通用历史)

`ext` 要支持 kz 的**两种** params(第三轮回填定稿):

- `{ stationId, metric? }` → 收益趋势(`biz/power/stationRevenueTrend`)
- `{ entity, keys, agg? }` → 通用归档历史(`tskv/{桶}/telemetry/…`)

第一版只做了收益趋势,开头就要求 `params.stationId`,通用形态一进来就抛错。**当场就会犯**:我们给她的样例工程第一页那张 30 天柱状图用的正是通用形态,两条序列全部报「数据不可用」,而且一个 kz 请求都没发出去(在发请求之前就抛了)。

多半不是她漏做:这条用例与配套测试桩是 `789471d`(09-06 23:02 美东 = 09-07 上午北京)才进包的,她的快照目录名是 `20260906`,大概率没有这条用例,本地跑是全绿的。**教训:给同事的 tarball 要带上生成时的提交号**,否则双方都不知道对着哪一版契约在写。

她的修复(`7801de3`):`params.keys` 是数组就走 `fetchKzTimeseries`,粒度映射 `1m/5m/1h/1d/1M/1y → minute/minutefive/hour/day/month/year` 与我们的 `LegacyDataSource` 完全一致;应用运行时走她的扩展服务地址,测试走注入 fetch。

镜像实测发出的请求:

```
/kzserver/tskv/day/telemetry/ASSET/95bf2370-…/values/timeseries?keys=tsPvPowerTotal&startTs=…&endTs=…&interval=86400000&agg=AVG
```

30 天窗口自动选 day 桶、间隔 86400000 毫秒、聚合 AVG,图出数,顶栏「1 个数据绑定不可用」消失。
