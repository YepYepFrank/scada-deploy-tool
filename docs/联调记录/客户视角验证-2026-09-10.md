## 3. 发现:TB 自己漏历史 —— 最新值 403,历史区间 200 带数据

查 §2 那三处「不可用」时发现的,与同事的实现无关,是 **TB 侧**的判定不一致。
同一个 CUSTOMER_USER token、同一台**未分配**设备、同一个 endpoint,只是查询参数不同:

```
GET /api/device/{id}                                        → 403
GET /api/plugins/telemetry/DEVICE/{id}/values/timeseries?keys=DC_V
                                                            → 403
GET .../values/timeseries?keys=DC_V&startTs=…&endTs=…&agg=NONE
                                                            → 200  {"DC_V":[{"ts":…,"value":"72.651"},…]}
```

三台设备都这样:`BS_2_CK`(未分配)、`Test Device A1`(未分配)、`RY_GZ_ESS_PCS`(Public 客户名下)。
**不是脚本串了 token**:同一次请求里 `/api/auth/user` 回的是 `CUSTOMER_USER`。

**影响是看得见的,不只是接口层**:第 2 页的 g1 / g2 两张图**把 `BS_2_CK` 的历史曲线画出来了**
(截图 `02-迁移验证.jpg` 里那两张有数据的图),角标只是说实时订阅不可用。也就是说
「客户看不到未分配设备的数据」这句话,在**历史**这一半上不成立。

复现一条命令:`node scripts/tb-verify-customer.mjs`(2026-09-10 已把这条检查加进去,最后一行)。

- 与 kz 待办 ⑤b 是**两件事**:⑤b 是 kz 不按归属过滤(今天复测仍在,`scripts/kz-ownership-check.mjs`);
  这条是 **TB 自己**。就算 kz 修好,这条不修客户照样读得到历史。
- 待查:是 CE 4.3.1 的既有行为、还是镜像上的某处配置。查清前**不要**对外说「客户只能看到分配给它的数据」。
