# DataSource 实现归属:LegacyDataSource 长期保留 · 2026-09-09

一天之内在这件事上翻过一次,两次的理由都记在这里,免得以后有人再提一遍。

**结论:`packages/tb-client/src/legacy-adapter.ts` 的 `LegacyDataSource` 长期保留,
定位从「T1.1 临时预案」改为「部署工具自用的数据源」,不再计划删除。**

## 1. 背景

`LegacyDataSource` 是 2026-09-05 立的预案:当时同事(庄艳芹)的 `TbClient` 还没交付,
为了不让里程碑 A 停摆,我们照契约自己写了一份 `DataSource`。计划 T1.1 当时写了一句
「同事版到位后:删 `legacy-adapter.ts`,`/dev` 与宿主改注入 `TbClient`」。

09-09 她的 `TbClient` 交付并通过一致性套件 15/15,那句话到了该兑现的时候。

## 2. 第一版决定(当天上午,已撤回)

查下来「直接删」执行不了:她的 `src/services/tbClient.js` 文件头 import 了
`@/core/request`、`@/core/runtime`、`@/services/thirdApi`,`@/` 是她工程的别名,
我们的仓库解析不了。

但耦合比看上去浅——类本身有 `useInjectedFetch` 开关,传 `fetchImpl` + `baseUrl` +
`kzBaseUrl` 就整个走标准 fetch,那三个模块一次都不会被调用(一致性套件就是这么跑的),
卡住的只是文件头那三行 import。于是提了个方案:请她拆成 `tbClient.core.js`(无 `@/` 引用)
+ `tbClient.js`(薄封装),我们改注入她的实现,删掉自己那份。请求文件是
`docs/给同事的-TbClient拆分请求-2026-09-09.md`。

## 3. 为什么撤回

**① 同事的反馈(她说得对)。** 原话:「目前这个 tbclient 在应用调用时会调用不同方法,
但我看说明里,要放到你这边维护,感觉上绕了一圈」。她维护、交给我们托管、再从我们这儿
引回去,每改一次都要过我们一道——对她的工作流是实打实的退步。这条不是感受问题,是事实。

**② 一条提方案时漏查的硬约束。** 请求文件里给了两个去处,「留在她仓库、发包给我们」是其中之一。
这条**根本走不通**:

| | |
|---|---|
| 我们的 CI | `.github/workflows/ci.yml` `runs-on: ubuntu-latest` —— GitHub 托管跑机 |
| 她的仓库 | `http://192.168.7.16:8000/Storage_Charging_Division/Storage_Charging_Web.git` —— 内网 Gitea |

GitHub 的跑机拉不到内网仓库,`pnpm install --frozen-lockfile` 装不上。唯一的绕法是把
tarball 二进制塞进我们仓库,那正是 09-06 那次「她手上的包比契约旧一版、`ext` 用例白卡一天」
的问题**变本加厉**——从一次性事故变成常态。

两个去处一个走不通、一个是她说的绕一圈,方案就没有立足点了。

**③ 「统一」的好处我原先高估了。** 提方案时我把「一份实现」算得太值。实际上:

- **换不来 T3.8 的 token 刷新。** 她的客户端同样只是调宿主给的 `getToken`
  (`await this.getToken()`,默认读 `micro-grid-token`),刷新本来就是宿主的事。
  我们独立大屏的刷新是自己实现的(`apps/deploy-tool/src/standalone/session.ts`),
  统一与否都得自己写。
- 剩下的好处只有「行为一致」,而**一致性套件 `@grid/tb-client/testing` 当初立起来就是干这个的**
  ——11 条契约用例,两份实现各跑一遍(我们 `test/legacy-adapter.test.ts`,她 `tbClient.test.js`
  另加 4 条 kz)。用现成的机制解决,不必为此重排两个仓库的关系。

## 4. 现在的定位

`LegacyDataSource` 只在**我们自己**三处使用:

| 用处 | 文件 |
|---|---|
| 编辑器「预览」(含客户视角) | `apps/deploy-tool/src/editor/PreviewPane.vue` |
| 独立大屏 `site.html` | `apps/deploy-tool/src/standalone/StandaloneApp.vue` |
| 渲染器 `/dev` 展示页 | `packages/renderer/dev/DevApp.vue` |

**它不进同事的产物**,这一点是查证过的,不是推断:

- 她的运行时代码从没 import 过 `@grid/tb-client`(`main.js` 与 `ScadaPageView.vue` 只引 `@grid/scada-renderer`);
- 她唯一碰到的是测试文件里的 `@grid/tb-client/testing`,而**那个子树不 import `LegacyDataSource`**(只在注释里提过);
- 渲染器对 tb-client 的四处引用**全是 `import type`**,打出来的 `packages/renderer/dist/index.js` 里 `LegacyDataSource` 出现 **0 次**、也没有对该包的运行时 import。

所以保留它对同事和高潮**都是零工作量**。代价全在我们自己:多维护一份实现,且它必须一直
过一致性套件。

  「同事版到位后:删 legacy-adapter.ts…」标为作废;附录清理表里 `legacy-adapter.ts` 从
  「(临时)」改为「长期保留」。
- 契约 `docs/契约-v1.md` §11 的 `DataSource` 一行同步。
- 源码里四处「同事版到位后删除 / T1.1 预案」的注释改掉(`tb-client/src/index.ts`、
  `legacy-adapter.ts`、`StandaloneApp.vue`、`renderer/dev/DevApp.vue`)——这类注释留着,
  下一个人照做就会踩空,和 09-08 那次「清单写 LegacyDataSource 无重连」是同一类问题。
- `docs/给同事的-TbClient拆分请求-2026-09-09.md` 顶部标为**已撤回**,正文保留作记录。

## 6. 教训

提跨团队的请求之前,先把**自己这边的硬约束查完**。这次是 CI 跑机够不着对方仓库——一条
`grep runs-on` 就能查出来的事实,却排在方案之后才查,差点让同事白做一遍工。
