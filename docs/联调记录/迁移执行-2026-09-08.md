# ADR-003 迁移表执行 · 2026-09-08(`tbsite migrate`)

> ADR-003 决定 3 一期「只生成不执行」,二期 backlog 里的「迁移表自动执行」本日落地:`packages/compiler/src/writer/migrate.ts` + CLI `tbsite migrate`。本记录是在镜像上的首次执行。

## 1. 用例:Phase 3 旧工具留下的无前缀 `pqSum`

镜像上 32 台仙人山 IED 同时有两套 `P+Q`:

| key | 来源 | 数据 | CF |
|---|---|---|---|
| `pqSum` | 08-28 Python 版工具发布(Phase 3) | 09-01 02:55 起,秒级(每台约 12.2 万点 / 6 天) | 32 台各 1 个,**一直在跑** |
| `calc_pqSum` | 09-07 03:41 本工具按 ADR-003 发布 | 09-07 03:41 起 | 32 台各 1 个 |

09-06 那次 publish 的 `renameTable` 为空——上一版 `siteConfig` 是 `BS_*` 站点,没声明过 `pqSum`,所以这批旧 CF 不在任何一版声明里,再发布的「清理旧输出」也不会碰它们。迁移表按 ADR-003 的格式手写(`sites/migrations/xrs-mirror-test.rename.json`,33 行:32 台 IED + `SSP1_DP1_IED1`)。

## 2. 执行

| 步骤 | 命令 | 结果 |
|---|---|---|
| dry-run 全表 | `tbsite migrate sites/xrs-mirror-test.tbsite.json` | 33 行 · **3 910 991 点**(每台约 12.2 万,区间 09-01 02:55 → 09-07 03:41「止于新 key 首点」;`SSP1_DP1_IED1` 0 点);页面文件里没有对旧 key 的绑定 |
| dry-run 限起点 | `… --table rename-one.json --from 2026-09-06T00:00:00+08:00` | 8 320 点(09-05 16:00Z 起) |
| **apply(1 台)** | `… --table rename-one.json --apply` | `SSP1_GP1_IED1.pqSum → calc_pqSum` 122 467 点,25 秒(123 批 × 1000 点) |
| 复核 | `tb-old-keys` | `calc_pqSum` 首点从 09-07 03:41 变为 **09-01 02:55**,与 `pqSum` 一致;再跑 dry-run 为 0 点(幂等) |
| **apply + delete-old(1 台)** | `… --table rename-one.json --apply --delete-old` | 0 点复制;删掉 `pqSum` 全部数据与同名 CF;设备上 CF 只剩 `calc_pqSum` |
| 复核(5 分钟后) | `tb-who-writes pqSum` | **`pqSum` 仍在更新**,规则链与 CF 里都没有它。再取最近 6 个点对比:`pqSum` 与 `P`、`Q` **同一毫秒**到达(03:47:58.241),`calc_pqSum` 晚 0.7 s(CF 算完才写),且 `pqSum`(80.14)≠ `P+Q`(78.22 = `calc_pqSum`)。**结论:`pqSum` 是模拟器原始报文里自带的 key,不是工具输出**;08-28 的同名 CF 只是又往同一个 key 上写了一遍 |
| 撤销误复制 | `tb-revert-copy` | `calc_pqSum` 在 CF 上线(09-07 03:41)之前的 122 467 个点是拷来的模拟器 `pqSum`,不是 P+Q,按区间删掉,首点恢复为 09-07 03:41;`pqSum` 09-01 → 09-07 的原始历史已被 `--delete-old` 删除,不可恢复(镜像 7 天 TTL 本也会清,模拟器还在持续写) |

**结论修正**:这份手写迁移表的前提错了——`pqSum` 从来不是工具的旧输出,而是模拟器报文里的原始测点,08-28 的 CF 与之重名。迁移表只能来自 `renameTable`(上一版声明 → 这一版声明),不能凭「看起来像旧输出」手写;`sites/migrations/xrs-mirror-test.rename.json` 已删除、不入库。`tbsite migrate` 本身的行为(复制区间、幂等、`--from`、`--delete-old`)在这次执行里都按设计工作,单测覆盖。

其余 31 台**没有执行**:全表 3.9M 点全量复制对镜像 TB 是一次明显的写入压力(09-05 才因 `ts_kv` 写满停过机),而镜像有 7 天 TTL,09-01 起的秒级旧点几天内就会被清掉,复制的价值有限。要清理它们只需 `--from <近几天> --apply --delete-old`(少搬、多删),建议在 W4 之前找个空闲时段跑;不清理的话每台 IED 多占 1 个 CF 槽位(上限 5)——但按上面的结论,这 31 个 08-28 的 `pqSum` CF 只是**多余的 CF**(输出与原始 key 重名),直接删 CF 即可,不需要迁移数据。同样性质的残留还有 Public 客户下的旧汇聚资产 `RT_TOTAL_P_TEST`(5 个 CF 在跑,`totalP*` 秒级写入),不在迁移表范围内,记入联调环境待办 ⑦。

## 3. 行为要点(与单测一致,`test/drift-migrate.test.ts`、`test/migrate-from.test.ts`)

- 只复制**新 key 首点之前**的旧点:新 key 上线后两边都在写,重叠段以新 key 为准,不覆盖;新 key 没数据则复制到现在。
- `--from` 再限定起点;分页 5000 点读、1000 点一批写;数值字符串转 number。
- `--delete-old` 只在 `--apply` 时生效:删同名 CF(按 CF 名 = 输出 key)与旧 key 全部数据。
- `--rewrite-pages`:页面文件里按「实体名 + 旧 key」对上的 `ts.key / ts-history.keys / ext.params.keys` 改名并写回文件,之后要 `tbsite page` 重新发布;dry-run 只列出来。
- 实体不存在 → 该行 skipped,退出码 1;其它行照常。

## 4. 同日一起落地

- `tbsite drift <站点>`:本地声明 / `pages/<站点>-*.pageconfig.json` vs 线上 `siteConfig` / `pageConfig` 的结构化 diff(实体引用归一为 `{type, name}`,不把发布回填的 id 当差异)。首跑:站点声明一致(历史 10 版)、`运营总览` 页面 version 1 一致、线上另两张页面(`总览`、`迁移验证`,当初从 `.scadaproj` 发布)本地没有文件。`publish` 前也会打印同样的差异摘要(仍以本地为准)。
- `PagePayload` 严格类型(`src/page/types.ts`):契约 §1–§3 的 TS 镜像,`collectEntityRefs` 顺带把 `ext.params.entity` 也纳入按名解析(ADR-002)。
